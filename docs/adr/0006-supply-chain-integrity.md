# 0006. Supply-chain integrity controls

Status: Accepted (2026-10-20)

## Context
A security tool is a high-value target: a compromised dependency, build action, or base image
would run inside the defender's environment. Version tags and floating dependency ranges can be
silently repointed or upgraded.

## Decision
1. **Hash-locked dependencies.** `requirements/runtime.txt` and `requirements/dev.txt` are
   generated by `scripts/lock.sh` (universal lock covering Python 3.11-3.13) and installed with
   `pip install --require-hashes`. CI fails if the lock files are out of date, and the pinned
   `uv` that generates them is itself hash-locked (`requirements/tools.txt`).
2. **SHA-pinned GitHub Actions.** Every third-party action is referenced by full commit SHA with
   the version in a comment; Dependabot proposes updates.
3. **Pinned container base image.** The Dockerfile pins the base image by index digest, builds in
   two stages, runs as a non-root user, and CI smoke-tests it on a read-only filesystem.
4. **Automated scanning.** `bandit` (static analysis), `pip-audit` (known vulnerabilities),
   Trivy (container image), and a CycloneDX SBOM are produced by CI.

## Consequences
- Builds are reproducible and tamper-evident at the dependency level.
- Updates are deliberate: lock files and action pins change only via reviewed commits.
- Maintenance cost: regenerate locks when dependencies change, and review Dependabot PRs.
- Residual risk: pins prove *which* artifact is used, not that it is benign; scanning and
  review remain necessary.
